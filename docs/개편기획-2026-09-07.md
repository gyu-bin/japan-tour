## 3. A · 살아있는 도시

### A-1. 공항 비행기

**지금:** `lmPlane()` 이 활주로 위에 **정지한** 여객기 하나를 놓는다.

**개편:**
- 활주로의 정지 기체는 그대로 둔다 (탑승 게이트 느낌)
- **이륙 루프**를 하나 추가 — 활주로 끝에서 가속 → 기수 들림 → 상승 → 화면 밖 → 리셋
- 상공을 가로지르는 **순항 기체** 1~2대. 하네다 조각이 화면에 없어도 하늘에 보인다

**적용 일차:** Day 01(하네다 도착), Day 06(하네다 출발). 순항 기체는 전 일차.

**구현:** `flyers` 배열에 `{group, t, speed, path}` 를 담고 `tick()` 에서 진행.
구름·관람차와 같은 패턴이라 새 개념이 없다. 프레임 비용은 무시할 수준.

### A-2. 지하철역과 전철

**막힌 것:** 도쿄 지하철은 지하라 `railway=rail`(지상 JR)로는 안 잡힌다.
지금 조각 16장 중 **5장이 철도 0개**다 — 롯폰기·teamLab·아자부주반·황거·후지.
롯폰기를 `railway=subway` 로 다시 조회하니 **노선 5개 + 롯폰기역 2개 노드**가 나온다.

**데이터 파이프라인 변경** (`tools/fetch-osm.py`)

```
추가 조회:
  way ["railway" ~ "^(subway|light_rail|monorail)$"]     지하철 노선
  node["railway" = "station"]                            역 (이름 포함)
  node["railway" = "subway_entrance"]                    출입구 (선택)

저장 형식 추가:
  {k:'subway', p:[...]}                    지하 노선 (지상 rail 과 구분)
  {k:'station', x, y, name, kind}          역 한 점
```

전 조각 재수집이 필요하다. Overpass 가 429 를 자주 뱉으므로 **20~30분** 잡는다.
기존 미러 순회·백오프 로직이 이미 있어 코드 변경은 조회문과 변환부뿐이다.

**렌더링** (`js/osm-tile.js` + 새 `js/transit.js`)

| 요소 | 표현 |
|------|------|
| 지상 철도 | 지금처럼 불투명 리본 |
| **지하철 노선** | 반투명 점선 리본. 지하라는 걸 시각적으로 구분 |
| **역** | 작은 플랫폼 + 지붕 + 노선색 표지 기둥. 스팟 핀보다 낮고 작게 |
| **전철** | 노선 폴리라인을 따라 왕복하는 3~4량 편성. 역에서 잠깐 정차 |

**전철 애니메이션:** 노선마다 `CatmullRomCurve3` 를 만들고 `t` 를 진행.
`getPointAt`/`getTangentAt` 은 이미 사람 산책에 쓰는 방식 그대로다.
역 근처에서 속도를 0 으로 떨어뜨렸다 다시 올리면 "정차"가 된다.

**일차별:** 그 일차의 조각에 속한 역·노선만 그린다. 조각이 없으면 아무것도 안 그린다.

**주의 — 라벨 충돌:** 역 이름을 다 띄우면 스팟 핀과 싸운다.
역은 **모형만** 놓고 이름은 생략한다. 확대(LOD)했을 때만 역명을 띄운다.

## 4. B · 톤 완성

### B-1. 물 (우선순위 높음)

지금 땅 끝이 곧 허공이라, 유기적 해안선을 만들었는데도 떠 있는 느낌이 남는다.
**땅보다 훨씬 큰 물 평면**을 깔고 시간대별로 하늘색과 맞춘다.
조각 데이터에 이미 `coast`(해안선) 피처가 있으니 오다이바는 실제 만 모양을 쓸 수 있다.

### B-2. 타이포 · UI

레퍼런스 인상의 절반인데 아직 손을 안 댔다.

- 세리프 제목 + **한자 병기** (`도쿄 / 東京`, `아사쿠사 / 浅草`) → `data.js` 에 `jp` 필드 추가
- 헤어라인 괘선, 카드 테두리 1px, 여백 확대
- 하단 일차 스트립을 레퍼런스처럼 지명 병기로

### B-3. 지형 높이 (선택)

땅이 완전히 평평해 종잇장 같다. 언덕에 아주 낮은 높이를 주면 실루엣이 생긴다.
효과 대비 비용이 커서 **후순위**.

## 5. C · 구조 정리

`index.html` 이 **2,400줄**이다. 이미 편집이 불안정해지는 구간이고, A·B 를 여기에 더 얹으면 악화된다.

**완료 (2026-09-07).** `index.html` 2,557줄 → **1,530줄**

```
js/core.js        three 기본 + 공유 헬퍼   90줄  ← 신규
js/lighting.js    시간대 프리셋            98줄  ← 분리
js/scenery.js     건물·나무·랜드마크·비행기 843줄  ← 분리
js/labels.js      라벨 겹침 정리           88줄  ← 분리
js/osm-tile.js    조각 렌더러             244줄  (그대로)
js/data.js        일정 + 투영             400줄  (그대로)
js/transit.js     역·전철                       ← 5단계에서 신규
index.html        조립 + UI + 배치       1,530줄
```

**`js/camera.js` 는 보류했다.** 카메라 코드가 `viewMode`·`sheetShownPx`·`dayLayout` 같은
UI 상태와 얽혀 있어, 떼어내려면 상태를 넘기는 배선이 코드를 줄이는 것보다 커진다.
지하철을 얹은 뒤 다시 판단한다.

**순수 이동**이라 동작은 그대로다. 6일차 × 시간대 7종 × 클로즈업 전수로 확인했다.

### 분리하다 걸린 것

- `declutterChips` 가 `markers`·`selIdx`·`panelEl`·`cam` 을 전역으로 읽고 있었다.
  의존성을 인자로 넘기게 바꿨다 (`declutterChips(dt, { markers, selIdx, zoom, panelEl })`)
- `lightOverride`(사용자가 고른 시간대)가 조명 블록에 섞여 있어 딸려 나갔다. UI 상태라 되돌렸다
- 등록부 배열(`peoples`·`stopBuildings`·`flyers`·`shadowSpots`)은 `const` 로 두고
  `length = 0` 으로 비운다. 재할당하면 import 쪽이 옛 배열을 계속 본다

**한자 병기 범위:** 확실한 지명·랜드마크만 넣었다 (일차 6 · 스팟 27 · 랜드마크 5).
식당 상호(몬자 젠야·토도로키·히로키야·스시하츠메 등)는 표기를 확신할 수 없어 비웠다 —
지어내면 틀린 정보가 된다. 아는 표기가 있으면 `data.js` 의 `jp` 필드에 넣으면 바로 뜬다.

**캐시 함정:** `python3 -m http.server` 는 캐시 헤더를 안 보내서 브라우저가 ES 모듈을
계속 옛 버전으로 물고 있었다. 이번 작업에서 헛짚게 만든 원인이라 `tools/serve.py`(no-cache)를 만들었다.

3번을 4·5번 앞에 두는 이유: 지하철은 코드가 상당히 늘어나는데, 2,400줄짜리 파일에 더 얹으면 그 뒤로 손대기 어려워진다.

## 7. 결정 (2026-09-07 확정)

1. **전철 대수** — **노선당 1대**
2. **역 이름** — **확대했을 때만** 표시. 스팟 핀과 안 싸우게
3. **한자 병기** — 미정. 6단계(타이포)에서 다시 묻는다.
   OSM 역 데이터에 `name`(漢字)·`name:en` 이 이미 들어 있어 **역 이름은 공짜**다

### 구현 중 알게 된 것

- 같은 역이 운영사별로 **노드 여러 개**로 매핑돼 있다 (아사쿠사역 4개, 아키하바라역 3개).
  렌더링 전에 이름 + 근접도로 합쳐야 한다
- 직교 카메라의 `far` 가 400 이라 넓은 바다가 통째로 잘려 나갔다. `-400 ~ 900` 으로 넓혀 해결
